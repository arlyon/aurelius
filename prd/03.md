## 1. Problem and evidence

The current extractor produces source-grounded candidate statements, but not consistently atomic assertions. Predicates such as `reporting_rule`, `reported_metric` and `planned_change` accept unrestricted text. A single object can therefore contain several requirements, observations, actors and conditions.

Examples observed in stored production candidates:

- One `reporting_rule` contains a Monday deadline, a prior-week reporting period, a Slack delivery instruction and a recipient.
- One `budget_literal` combines a monthly budget with a two-month ramp duration.
- An account-ownership statement is stored as a paragraph under `reported_issue` rather than as `account → owned_by → organization`.
- A provider entity named LinkedIn is used as the subject of a pause statement that actually concerns scoped advertising activity.

The frozen 100-window v11 evaluation returned 69 candidates versus four in its earlier strict baseline. A same-assistant source review classified 58 as useful source-local claims and 11 as requiring review or exclusion. Those counts are **not atomic-fact counts, independent gold labels, precision certification or recall measurements**.

The candidate-only production Job was suspended at the operator's request; its pod was verified absent with zero active workers. Raw-source ingestion remains separate and must stay operational. Existing statements and the durable spend ledger must be preserved.

## 2. Product outcome and users

An operator or downstream agent can inspect one candidate as:

> A specific subject has one declared relationship to one correctly typed object, under explicit qualifications, supported by source evidence.

The same assertion has three consistent views:

1. Validated JSON.
2. A subject–predicate–object table.
3. Deterministically rendered, readable text with source citations.

Primary users are reviewers deciding whether a candidate is useful and correct, developers debugging extraction, and later consumers querying accepted structured knowledge. Acceptance into canonical memory is outside this PRD.

## 3. Scope and non-goals

### Included

- One common SPO assertion shape, specialized by predicate definitions.
- Predicate-specific subject types, object schemas, normalization rules and renderers.
- Eager within-payload entity declaration through a top-level `local_entities` array, with source-coordinate identity and reusable request-local references.
- Source-scoped entity references, including verified source-record references where a real source anchor exists.
- Atomic decomposition within one native, strict, predicate-specific structured-output generation call.
- Per-assertion intent, polarity, conditions, attribution and valid-time handling.
- Deterministic semantic validation, action-group completeness, rendering, coordinate-based duplicate consolidation and strict review items.
- Preparer-issued Markdown span links for deterministic evidence resolution without post-generation string matching.
- Offline golden cases and evaluation on the existing frozen 100 windows.
- Versioned candidate artifacts and explicit mixed-version handling.

### Excluded

- A second model call for atomization, criticism, repair, identity resolution or rendering.
- A new general-purpose frame language, arbitrary argument maps or rule engine.
- Generic `notes`, paragraph-valued catchalls or prose fallback objects in the generation schema.
- Loose JSON mode, permissive per-item structural parsing, structural repair or a second parsing tier as a fallback for native schema enforcement.
- Fuzzy quote matching, whitespace alignment, occurrence repair or model-generated byte offsets in the atomic evidence path.
- Adopting ORM, SBVR, RDF, Wikibase, LinkML or a new graph database as infrastructure.
- Automatic canonical identity merges, truth promotion or accepted-fact writes.
- Canonical database migrations, new grants, re-embedding or raw-source modifications.
- Expanding chunk context across unrelated documents or tenants.
- Automatically restarting the suspended extraction Job.
- Treating sentence count or punctuation as a proof of atomicity.

## 4. Domain terms

| Term | Meaning |
| --- | --- |
| Assertion | One predicate application between a subject and an object, with qualifications and evidence. It is initially an unreviewed candidate, not established truth. |
| Atomic | The assertion expresses one independently assertable relationship. Its object is not a container for additional independent claims. |
| Predicate specialization | A declared predicate determines admissible subject types, object structure, normalization and rendering. |
| Typed value | A cohesive value such as money, duration or a weekly local time. Multiple necessary fields do not themselves make a value non-atomic. |
| Source-local entity | An entity declared once in `local_entities`, anchored to issued source coordinates and referenced by local ID across assertions; not a canonical identity claim. |
| Span reference | A preparer-issued href such as `span:100-150`, resolved through the current request's immutable span catalog to an exact original UTF-8 byte range. |
| Complete action group | The assertions associated with one resolved action identity, satisfying that action type's declared minimum semantic payload. |
| Qualification | Information determining how an assertion must be interpreted: intent, polarity, conditions, attribution, semantic scope and valid time. |
| Evidence | An issued span reference resolved by Rust to the source identity/revision, exact UTF-8 byte coordinates and original quote. Evidence text is not the assertion's object. |
| Review item | A strict object containing an intended predicate, an issued span reference, its exact quote and an enum failure reason. It is not an atomic assertion or a generic prose escape hatch. |

Tenant authorization scope and semantic ownership are distinct. An organization's right to access a source does not establish that the organization owns every metric, account or campaign mentioned in it.

## 5. Assertion contract

### 5.1 Common grammar

```text
Assertion<P> =
    Subject<subject-types(P)>
    + Predicate<P>
    + Object<object-schema(P)>
    + Qualification
    + Evidence[1..n]
```

There are exactly three primary semantic parts: **subject, predicate and object**. Qualifications and evidence are not an open-ended substitute for additional predicates.

The generation envelope has three required arrays: `local_entities`, `assertions` and `review_items`. There are no generic `notes` or fallback fields. Illustrative instance; labels and coordinates stand for entries already issued by the preparer, not existing canonical IDs:

```json
{
  "local_entities": [
    {
      "id": "local_1",
      "entity_type": "report_schedule",
      "identity_span_ref": "span:0-50",
      "action_kind": null
    }
  ],
  "assertions": [
    {
      "subject": {"ref": "local_1"},
      "predicate": "pull_deadline",
      "object": {
        "kind": "weekly_local_time",
        "weekday": "monday",
        "local_time": "16:00",
        "timezone_text": "PT"
      },
      "qualification": {
        "mode": "required",
        "polarity": "positive",
        "conditions": [],
        "attribution": [],
        "validity": {"from": null, "to": null}
      },
      "evidence": ["span:100-127"]
    }
  ],
  "review_items": []
}
```

Rust resolves local IDs through the declared entity array and resolves hrefs through the preparer-owned span catalog. It hydrates source identity, revision, exact quote and byte coordinates by lookup, never by searching for model-generated text. Local IDs cannot grant authority or introduce canonical identities. Undeclared references, duplicate declarations and inconsistent bindings fail semantic validation; IDs are not silently guessed or repaired.

### 5.2 Predicate definitions

A predicate definition MUST specify:

- Stable name and semantic description.
- Admissible subject entity types.
- Object schema, including allowed values and required fields.
- Supported qualifications and any restrictions on their use.
- Allowed deterministic normalization and source-grounding requirements.
- Rendering definition and required value formatters.

Use **standard JSON Schema through the model's native strict structured-output facility**. One authored predicate definition must drive the native generation schema, canonical Rust data representation and renderer bindings. Every object is closed to additional fields; required fields, predicate-specific alternatives, object types and enum values are enforced during the single generation pass. Schema references are local only.

Do not implement permissive JSON mode, a loose intermediate representation, per-item structural salvage, structural repair or a second model/parser pass. If the configured model/gateway cannot enforce the required strict schema, block the atomic extraction path with `native_schema_unsupported`; do not silently downgrade. Provider compatibility must be proven before any authorized evaluation.

Rust still performs deterministic **semantic checks** on the one canonical typed result: issued-marker lookup, local-reference integrity, scope, source grounding, qualification semantics, action completeness and deduplication. These checks are not a second structural parsing tier. An unexpected malformed envelope or provider refusal is a response-level protocol diagnostic with private raw retention and no retry.

The offline v1 baseline is frozen in `lanes/examples/atomic_spo.json`, with synthetic source/expectation cases in `lanes/tests/fixtures/atomic-golden.json`. These definitions cover the families below; they are not a claim of model quality or independently reviewed client-source labels. Review the definitions and real-source expected atoms before paid model testing.

| Predicate | Subject | Object |
| --- | --- | --- |
| `pull_deadline` | Scoped reporting task/schedule | Weekly local time |
| `coverage_period` | Scoped reporting task/schedule | Relative reporting period |
| `delivery_channel` | Scoped reporting task/schedule | Declared channel code/reference |
| `delivery_recipient` | Scoped reporting task/schedule | Person reference |
| `ranking_metric` | Scoped ranking specification | Declared metric code/reference |
| `owned_by` | Platform account | Organization reference |
| `monthly_budget` | Scoped budget/plan | Money-per-month value |
| `ramp_duration` | Scoped plan | Duration |
| `operational_status` | Scoped campaign/channel activity | Declared status enum |
| `executor`, `recipient`, `target` | Source-scoped action | Appropriately typed entity reference |

A provider is not a campaign activity. A person is not an arbitrary verb phrase. A phrase such as “Budget increase” is not automatically an identified budget entity.

Generic `notes`, free-form explanations, paragraph-valued properties and unmapped-prose objects MUST NOT exist in the atomic generation schema. Named textual value kinds may represent constrained names or codes only where a predicate explicitly requires them; they are not descriptions or instruction containers. A length limit alone does not establish atomicity. Material that cannot fit a specialization must use the strict `review_item` contract below and must not count as a fact.

### 5.2.1 Strict review items

A `review_item` MUST contain exactly the declared fields, including:

- `intended_predicate`: a bounded predicate identifier. It may name an unsupported specialization **only in this review channel**, never in `assertions`.
- `span_ref`: an exact href issued for this request.
- `exact_quote`: the exact original quote belonging to that href, checked by direct equality against the catalog; no searching, fuzzy matching or whitespace repair.
- `reason`: one enum member, initially `missing_executor`, `missing_target`, `invalid_target`, `unsupported_predicate`, `unsupported_condition`, `unsupported_outer_negation`, `ambiguous_scope`, `unresolved_entity`, `invalid_span_ref` or `action_incomplete`.
- `action_ref`: the affected local action ID or null, to support grouped review without a prose explanation.

All fields above are required in JSON Schema, with `additionalProperties: false`; `action_ref` is explicitly nullable rather than omitted. The same shape is used for model-declared reviews and server-generated semantic rejections where trustworthy predicate/evidence data is available. Failure reasons are a closed, versioned vocabulary. An item with an unresolvable marker or malformed review structure cannot be laundered into a valid review object: retain it privately as a protocol diagnostic, without inventing a source quote. There is no free-text `reason`, `notes` or `explanation` field.

### 5.3 Entity references and complex actions

- The model MUST declare each source-local entity once in the top-level `local_entities` array, then reuse its ID in every related assertion. Each declaration has a unique request-local ID, an allowed entity type and an issued `identity_span_ref`.
- Resolve the complete local reference graph eagerly before semantic validation of assertions. Reused IDs point to one declaration; duplicate IDs, undeclared IDs and inconsistent types are invalid. This is intra-payload resolution, not a global entity-resolution model pass.
- References MUST resolve to those declared source-grounded entities. Trusted input-provided entity/record identities may be bound through their actual issued source anchors; neither a canonical ID nor a record ID substitutes for the required grounding coordinates.
- Record metadata may establish source identity, such as an Asana task. It is not evidence that a requested business action occurred.
- NLP mentions and coreference clusters remain hypotheses. Neither name equality nor a cluster score authorizes a canonical identity merge.
- Model-created canonical IDs and unrestricted entity invention MUST be rejected.
- Source-local facets such as a report's ad-group ranking need an explicit parent record and source-supported facet kind.
- An action needing executor, recipient and target uses a source-scoped action declaration with separate qualified triples that all reference that same local entity. The same call emits the declaration and assertions; no extra model pass is introduced.
- An unknown required referent or owner goes to review. Do not substitute the tenant, agency, provider or document author merely because it is available.

### 5.3.1 Minimum viable completeness for actions

Each supported action type MUST declare its minimum semantic payload before model testing: the action kind and core target/purpose, plus whichever roles that action type requires, such as an executor for an assignment. Optional scheduling or delivery details must not be mistaken for the core payload.

Validation MUST resolve entity identities, validate individual assertions, then validate the action group **before any member is persisted as a surviving assertion**. If the action kind, target or another required core role is absent, unsupported or rejected, reject **all assertions associated with that action**. Do not keep an executor, recipient or deadline for an action whose meaning has been lost.

Grouping and rejection propagation operate on resolved source-coordinate identity, not ephemeral IDs; declaring the same broken action under a second local label cannot bypass completeness checks. References to a rejected action must not survive as dangling facts. Independent complete actions and unrelated assertions in the same response may survive. Rejection of an optional detail does not invalidate a complete core unless the action definition declares that dependency.

Example: if a send-report action's report target fails validation, its otherwise valid `executor → Megan` and `recipient → Ani` triples are also rejected. Emit strict review items with the intended predicates, exact evidence and `invalid_target`/`action_incomplete` reasons. Do not store a graph that merely says someone executes an unknown action.

### 5.4 Qualifications and values

- Modes MUST distinguish asserted, planned, required, requested, preferred and hypothetical propositions. Reported attribution is separate from whether the underlying action is planned or completed.
- Polarity MUST be explicit. **`mode = required` plus `polarity = negative` means prohibition: required(not P), or “must not.”** It never means not(required P), or “not required.”
- The v1 schema intentionally has no representation for absence of obligation or unsupported outer negation. Such source material MUST fail assertion validation and become a strict review item with `unsupported_outer_negation`; it must not be flattened into a prohibition, a positive assertion or an empty result.
- Conditions MUST attach only to the assertions they qualify. For example, “Snitcher/RB2B once live” must not make the entire weekly report conditional. Only declared typed condition forms are supported; no prose condition catchall is allowed. Unsupported conditions route to `review_items` with `unsupported_condition` instead of being discarded or applied too broadly.
- Attribution MUST preserve an explicit reporter or requester without turning that person into the executor, owner or measured subject.
- Source publication time, retrieval time and business valid time MUST remain distinct. Missing validity remains unknown.
- Preserve date precision, unresolved years, timezone text and temporal ambiguity. Do not infer a year for “July 1,” an IANA zone or UTC offset for “PT,” or business validity from a task's due-date header.
- Money normalization MUST preserve amount, currency evidence and recurring unit. `$` alone does not authorize an ISO currency code. Total budget and budget delta are different predicates/values; arithmetic derivations are not extracted source assertions.
- A monetary quantity or local schedule is a cohesive structured value, not an excuse to bundle a ramp duration, recipient or unrelated requirement into the object.

### 5.5 Coordinate-based identity and deduplication

After local reference resolution, entity identity MUST be based on its exact source anchor: authorized source/document identity, revision/content identity, and original UTF-8 byte start/end coordinates. The document identity is tenant-scoped. Do not hash a model's `local_1` label, array position, display label or paraphrase as entity identity.

The assertion identity key consists of:

```text
semantic contract/predicate version
+ resolved subject source coordinates
+ predicate
+ normalized typed object (or resolved object source coordinates)
+ semantic scope and qualifications
```

All entity references inside objects, qualifications and scope must be resolved before hashing. Money/time normalization follows the predicate's declared rules; canonical serialization is independent of object-key order. Reordering `local_entities`, renaming `local_1` to `local_9`, or referencing an equivalent declaration for the **same exact source anchor** must not change the assertion hash.

Different source coordinates, revisions, subjects, typed values, intent, polarity, conditions or validity must remain distinct. Coordinate identity does not prove that different mentions or documents refer to the same real-world entity; cross-coordinate/canonical merging remains deferred. Supporting evidence href order, repeated evidence and renderer wording are not assertion identity. Identical resolved assertions consolidate their evidence.

### 5.6 Preparer-issued Markdown span links

`fact_preparation.rs` MUST create the span catalog and annotated model input **before generation**, for example:

```text
[Pull stats Monday by 4pm PT](span:100-127)
```

The example coordinates stand for the actual original source span. They are document-global, UTF-8 byte offsets, start-inclusive and end-exclusive, never positions in the Markdown-annotated view. The authoritative catalog maps each issued href to the original document/revision/content hash, byte range and exact raw quote.

- The model copies issued href strings into entity anchors and assertion evidence. It does not count characters, tokenize output, invent offsets or reconstruct source quotes for successful assertions.
- Rust resolves a returned href by exact catalog lookup. A syntactically plausible but unissued href is invalid, even if its numeric range would fall somewhere in the document.
- No fuzzy matching, whitespace normalization, quote search, nearest-occurrence selection, span expansion or v11 alignment fallback is allowed in the atomic path. Source extraction and typed-value normalization are separate from evidence identity.
- The preparer must expose adequate bounded evidence units and entity/action anchors for the supported golden cases. Overlapping anchors belong in an explicit flat span catalog rather than invalid nested Markdown links. Coarse preparation must not force invented subspans or hide coverage loss.
- Preserve original source bytes, embedding chunks and citations unchanged. Markdown links are a model-input view only. Existing local NLP may help select spans during preparation; it is not used to repair returned evidence.
- Escape literal source Markdown and link-like text so source-authored `span:` strings cannot become trusted markers. Only the preparer's catalog grants marker validity. Escaped display labels are not the authoritative quote.
- An original span, including a verified record anchor supplied as bounded context, may be referenced without its label being repeated in every assertion's evidence. Each assertion must still have semantic evidence for the relationship; document co-location alone is insufficient.
- If a required entity or record has no valid source-coordinate anchor, route to review rather than synthesize a zero-length span or hash an ephemeral identifier.

## 7. Deterministic rendering

The structured assertion is authoritative. Text is a view, not a second source of truth.

- Predicate definitions supply a small, non-executable rendering definition using named placeholders and approved typed formatters.
- The renderer centrally preserves mode, polarity, condition scope, attribution and valid-time qualification. A template cannot silently omit them.
- Unknown/source-local identities must render honestly, for example “the account referenced in this source,” not an invented canonical account name. Rendering resolves entity labels through the validated `local_entities` bindings, never through an unvalidated model ID.
- Incomplete action groups and review items must not be rendered as surviving facts. Prohibitions must render as “must not”; an unsupported absence of obligation must remain a review item.
- Values and labels must be escaped for the output context, including Markdown/TUI output. Source text must not become executable template syntax or an external mention.
- Renderer changes must not require another generation request or change assertion identity. Renderer versions are separate from extraction/semantic-definition versions.
- No Java/Haskell runtime, general expression evaluator or natural-language generation framework is required for the initial implementation.

Required rendering examples:

| Structured meaning | Required distinction in text |
| --- | --- |
| Required reporting deadline | “The source requires this reporting task to be pulled by Monday at 4pm PT.” |
| Planned monthly budget | “The plan proposes a monthly budget of $50,000.” Not “the current budget is $50,000.” |
| Reported account ownership | “Jordan reported that Acme Media owned the referenced ad account.” Not independently verified or necessarily current ownership; names are synthetic. |
| Required negative ranking metric | “The source requires that these ad groups not be ranked by CTR.” |
| Conditional action | Preserve the specific executor/target and the prerequisite; do not render the condition as completed. |

## 8. Architecture and alternatives

Keep real FCoref/nlprule analysis, guarded transport, original source integrity, private artifacts and candidate-only persistence where applicable. Add the issued span catalog in preparation. The atomic path must not reuse v11's loose JSON structural salvage or quote-alignment fallbacks.

```text
original source + bounded record context + local NLP
    → preparer-owned span catalog and Markdown-linked source view
    → one native strict JSON Schema generation request
    → canonical typed envelope: local_entities / assertions / review_items
    → exact marker lookup and eager local-reference resolution
    → semantic checks and minimum-completeness validation by action group
    → coordinate-based assertion hashing and evidence consolidation
    → versioned atomic candidates / strict review items
    → JSON, SPO table and deterministic text views
```

The predicate definition is the shared seam for extraction constraints, runtime validation and rendering. Avoid duplicate vocabularies and validation logic spread across CLI, worker and lab callers.

Alternatives considered:

- **Prompt-only atomization:** minimal code, but leaves paragraph objects structurally admissible. Rejected as the primary solution.
- **Statement extraction followed by a model atomizer:** extra inspection stage, but another paid call and another opportunity to lose information. Rejected for this iteration by the operator's one-call constraint.
- **General n-ary frame grammar or full semantic-web stack:** expressive, but broader than the agreed SPO specialization. Not required.
- **Selected approach:** one SPO shape with predicate-dependent subject/object types, native strict schema enforcement, eager local entities, issued evidence markers, action-group completeness, coordinate-based identity, qualifications and deterministic rendering.
- **Rejected fallback:** permissive JSON or a complex second parsing/repair tier when native structured output fails. Unsupported capabilities block the path instead.

## 9. Data, versioning and compatibility

- Introduce a distinct candidate contract, provisionally `atomic-spo-v1`, with an explicit semantic-definition version/profile.
- Preserve original normalized sources, raw statements, candidate artifacts, citations and budget ledgers. Do not destructively convert old paragraph candidates by sentence splitting.
- Store the new format as versioned candidate artifact data using the existing artifact facilities. No canonical-table migration or accepted-fact materialization is included.
- Readers must dispatch by contract version or return an explicit unsupported-version result. No silent old/new reinterpretation is allowed.
- Re-extraction must use original source text and approved context, not treat earlier generated statements as new evidence.
- Assertion identity must be deterministic within its source revision and semantic contract using the coordinate-based key in §5.5. Model-local entity labels and generation order must not affect hashes. Repeated evidence may be combined only for an identical resolved scoped assertion and qualifications.
- Persist hydrated source coordinates/quotes and validated local-entity bindings, not bare ephemeral IDs or a dependence on a transient Markdown view. Preserve strict review items separately from surviving assertions.
- No partial action group may be published as surviving candidates before its completeness/dependency checks have succeeded.
- Rendering wording, evidence ordering and display labels must not independently create new logical assertions or trigger paid re-extraction.

## 10. Security, privacy and operations

- Authenticated tenant/principal scope is supplied by trusted callers, never by model output or source instructions.
- Semantic ownership cannot be inferred from authorization scope, document membership or the availability of an entity ID.
- Source and canonical context remain untrusted data, not instructions. Canonical context is not source evidence for a new assertion.
- Credentials, source payloads and private client fixtures must not enter public logs or Git. Preserve private directories/files and safe diagnostics.
- JSON Schema references must be local and bounded; no network resolution or executable schema/template extensions. Evidence `span:` hrefs are a distinct preparer-owned allowlist, never fetchable URLs or authority to read arbitrary ranges.
- Bind the span catalog to the exact tenant, source document/revision/content hash and request context. Reject cross-document, stale, invented or source-injected hrefs even when their numeric coordinates look valid.
- Enforce bounds on entity declarations, assertions, evidence, schema depth, input/output sizes and rendered output. Bounds must yield explicit review/failure results, never silent truncation presented as complete extraction.
- Keep current token/call/deadline guards available for later authorized evaluations. No automatic retry or second request may bypass the one-call requirement.
- If Temporal orchestration is later changed, preserve determinism and use the repository's patching policy. This design does not require changing existing workflows.
- Observability must separate requests, valid assertions, review items, rejects, unresolved bindings, source coverage and token cost. Candidate count is not a quality score.

## 11. Acceptance criteria

1. **R1:** A mock transport observes exactly one generation request for an eligible chunk, including malformed-output cases; input review may produce zero requests. Rendering and replay produce zero requests.
2. **R2:** The outgoing request uses the model/gateway's native strict JSON Schema facility, not loose JSON mode. The schema closes all objects and predicate-specific alternatives. An unsupported strict schema, refusal or malformed envelope produces an explicit response-level diagnostic without structural salvage, downgrade, repair or retry; semantic errors in a structurally valid envelope use strict review items.
3. **R3/R5:** Golden reporting cases produce separate assertions for deadline, coverage, delivery and ranking. “Not CTR” and “once live” retain their correct scope.
4. **R3:** A planned monthly amount and a two-month ramp produce distinct assertions. The amount's currency and recurring unit remain a single cohesive value.
5. **R4:** A paused LinkedIn activity cannot bind to the LinkedIn provider; wrong agency/client metric ownership, verb-phrase person labels and invented canonical IDs cannot pass the golden cases.
6. **R4:** A source task/entity is declared once in `local_entities` and reused across assertions. Every reference resolves to a unique declaration and real issued identity anchor; duplicate/undeclared IDs and inconsistent bindings fail validation. A verified task anchor need not be repeated in every evidence span, but its metadata does not prove completion of requested work.
7. **R5:** Requester/executor distinctions, hypothetical causes, partial/full access and unresolved validity survive extraction and rendering. `required` + `negative` renders prohibition. “Not required” and other unsupported outer negation cannot enter `assertions` and produce `unsupported_outer_negation` review items. Unsupported conditions produce `unsupported_condition`, not untyped text or silent omission.
8. **R6:** Preparation emits Markdown span links over original UTF-8 byte coordinates. Entity/evidence hrefs resolve by exact catalog lookup, including Unicode, repeated text, escaped Markdown and overlapping-catalog cases. Invented, stale, cross-source or source-injected markers fail. No matching or normalization of model-generated quotes is used to recover evidence.
9. **R7/R8:** Every supported predicate has rendering tests for its admissible qualifications. Re-rendering is byte-stable for fixed inputs/version and does not change meaning or issue network requests.
10. **R9:** Rejecting an action's core target, kind or another declared mandatory role rejects every assertion in that resolved action group, including otherwise valid executor/recipient triples. Independent complete actions and unrelated assertions survive. Optional-detail rejection follows the action definition's dependencies. Strict review items retain intended predicate, exact quote, issued marker and enum reason; no `notes` or prose fallback is accepted.
11. **R10:** Renaming or reordering local IDs leaves assertion hashes unchanged when source coordinates and meaning are identical. Changing source anchor/revision, object, scope or qualifications changes identity. Referenced object/qualification entities also resolve to coordinates; exact repeats consolidate evidence without treating distinct mentions as the same real-world entity.
12. **R11:** Old v11 statements and new atomic candidates coexist without silent conversion. Unsupported versions fail explicitly, and renderer-only changes do not trigger generation.
13. **R12:** Offline implementation and tests do not resume the suspended Job, write accepted/canonical facts, modify raw sources or change embedding profiles.

## 14. Risks and decisions still to approve

- **Predicate coverage:** an overly narrow vocabulary can improve apparent precision by discarding useful information. Preserve it through strict predicate/quote/reason review items, not a generic prose field, and measure omissions.
- **Semantic atomicity:** typed values prevent many bundles but cannot prove the proposition is correct or independent. Source-reviewed cases remain mandatory.
- **Entity binding:** declaring an entity once improves graph consistency but does not prove identity or ownership. Coordinate identity deduplicates exact anchors only; different mentions need separate future resolution. Unknown scope remains reviewable.
- **Evidence granularity:** issued markers eliminate output-side offset/whitespace guessing, but coarse or missing source spans can still lose coverage. Golden cases must verify preparation supplies the anchors needed for the intended assertions without exposing unrelated context.
- **Action completeness:** accepting roles independently can produce useless graphs. Every action type needs reviewed minimum-payload and dependency rules before it is enabled.
- **Qualification complexity:** modal negation, nested conditions and contradictory source passages may exceed v1. Unsupported cases must be explicit rather than flattened.
- **Model schema support:** native strict schema enforcement through the configured model/default gateway is a release blocker until demonstrated. Use a supported strict subset from the same definition; never downgrade to JSON mode, duplicate the structural grammar in a permissive parser or add a repair call.
- **Rendering:** a fluent sentence can overstate source certainty. Semantic preservation takes precedence over stylistic polish.

The operator approved completing and committing the offline iteration. Its baseline supports the predicate families in §5.2, typed conjunctions of `operational_status` premises only (no nesting, OR or prose), and source-anchored `send`, `update` and `investigate` actions. `send` requires executor, target and recipient; `update` and `investigate` require executor and target. Each kind also restricts target types and source verb forms; core roles must share event qualifications. Invalid required members reject the entire resolved action/dependency group; optional-role failure does not. Facets have declared source vocabulary and an explicit hydrated parent-record anchor. These rules are authored once in the JSON registry. Proposed semantic evaluation gates and real-source gold review remain unapproved qualification work. The seven operator amendments are incorporated as mandatory constraints: strict review items, action completeness, native schema enforcement, eager local entities, coordinate hashes, prohibition-only negative requirements and preparer-issued evidence links. Live evaluation budget, production resumption, canonical materialization and any future database migration remain separate decisions.

## 15. Prior art

This is an application profile of existing ideas, not a new general knowledge-representation language:

- [ORM / SBVR](https://www.omg.org/spec/SBVR/): fact types, roles, constraints and verbalization; especially the distinction between facts and operative requirements.
- [Wikibase data model](https://www.mediawiki.org/wiki/Wikibase/DataModel): typed statement values, qualifiers and references. Its model is inspiration, not a complete representation of our modal semantics.
- [JSON Schema](https://json-schema.org/draft/2020-12): structural contracts; not a proof of atomicity or entailment.
- [LinkML](https://linkml.io/linkml/generators/json-schema.html): schema-first modeling and JSON Schema generation, if catalog scale later justifies another authoring tool.
- [Grammatical Framework](https://www.grammaticalframework.org/doc/tutorial/gf-tutorial.html): separation of typed abstract representation from concrete language rendering.
